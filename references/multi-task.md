# 多任务写代码：lead 加实现方

两个以上写任务时用。主路由当 lead（拆任务、写契约、验收、合并），子 agent 当实现方。

## 同步，不是接力

实现方做完一个任务，不停下来等验收，立刻开始下一个。lead 验收和派工互不阻塞。

为什么：验收经常慢，接力的话实现方就一直闲着。两条线各跑各的，只用在制品上限当刹车。

## 任务板

`BOARD.md` 是唯一的共享状态，放在仓库里，历史本身就是协作记录。

```
在制品上限: 2        当前未验收: N        已完成: X/Y
```

| # | 任务 | 归属 | 状态 | 提交 | 依赖 | 可写路径 |
|---|---|---|---|---|---|---|
| T1 | 一句话说清做什么 | 主力子 agent | 已验 | `66b46ef` | 无 | `src/a.ts` |
| T2 | 一句话说清做什么 | 主力子 agent | 在途 | | T1 | `src/b.ts` |
| L1 | 跨缝测试 | lead | 已验 | `4e2cab3` | 契约 | `tests/seam.test.ts` |

状态：`待派`、`在途`、`条件通过`（逻辑验过了，要真实环境的部分还在排队，写清还差什么）、`已验`、`打回:原因`。

## 派工的硬规则

1. **在途任务的可写路径必须不相交。** 合并冲突里双方都可能丢东西，解冲突的人未必看得出来。答不上来"这个任务能不能完全不碰别的在途任务的文件"，说明还没拆完。确实要碰的，排到最后单独派。
2. **依赖还没验收的任务不派。** B 依赖 A 时先派 B，等于赌 A 是对的；A 被打回，B 要连带返工。
3. **派工单不能自相矛盾。** 要求加一个界面上显示的东西，又禁止碰界面文件，它只能二选一。
4. **未验收的任务不超过 2 个。** 满了不是让实现方闲着，而是 lead 立刻去清欠。否则实现方一路做到第七个，第二个被打回时，后面五个全建在错的地基上。

## 跨缝测试由 lead 写

两边各自的测试只覆盖自己那半边，缝正好没人负责。实现方写自己任务的单元测试，lead 写跨缝测试，而且现在就写，不等实现落地。它还是契约的第一个使用者，契约有洞会在这里先暴露。

报错信息要带实现方能定位的名字，只报内部 id 的话它只能猜。

## 验收之后的四种处置

| 处置 | 什么时候用 |
|---|---|
| 转正 | 验收全过 |
| 条件通过 | 逻辑对，真实环境的验证排队 |
| 打回 | 有实质缺陷，退回原任务。顺手补一道能抓住它的自动检查 |
| 拆分 | 任务本身定义得太大或太糊 |

转正时发现的新信息也要回头改任务板和契约，否则下一个任务就建在过期的前提上。

## 刹车

- 同一任务打回 2 次换人做，3 次停下来报给用户。
- 总任务数上限 20，单任务墙钟 60 分钟。
- 合并不放进循环。合并不可逆，由 lead 在循环外做，或者交给用户。

## 立刻停下的三种情况

| 情况 | 为什么 |
|---|---|
| 契约需要变更 | 继续跑只会产出更多建在旧契约上的代码 |
| 要动用户的环境 | 不可逆，用户可能不在场 |
| 测试在实现方没碰的那半边红了 | 说明 lead 那一半也坏了，两边都不可信 |

## 常见的坑

- **lead 的工作目录别停在实现方的 worktree 里。** 如果有回合结束时自动提交的钩子，会把实现方没写完的文件提交掉。看完就退回主仓库。
- **派工前先把验收命令在现有代码上跑一遍。** 确认它能启动，失败原因是功能还没写，不是路径或导入写错了。否则几轮都卡在同一个错误上，实现方的代码一次都没被验到。
- **测试一次查整份产物时，别人的已知问题会算到当前任务头上。** 循环永远等不到全过。只报告本任务负责的部分。
- **测试被打断后，它拉起的子进程可能留在后台。** 写跨缝测试时调子进程一律给超时。清理目录删不掉、或测试明显变慢时，先查有没有残留进程。
