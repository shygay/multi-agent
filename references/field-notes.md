都是作者实测的，环境是 Windows。

## 判定用例

- 主力子 agent 第一轮 14/16，误拆 0 次。多条任务被整体判成不派，点名外部模型审查时走错了路。补了"逐条判断、规模不清先看"和审查的规则后，第二轮 16/16。这只说明规则没有歧义，不代表主路由的实际判断。
- 主路由新会话跑 1 次，16/16，误拆 0 次。它是被问到才判断，提示词也明说了是路由判定，所以只说明它知道该怎么判，不说明真实工作时也会这样做。
- 规则改成不绑定具体 AI 的写法后，子 agent 再跑 2 轮：15/16，误拆 0 次。"这次大改拆成几个任务"这条有一轮选择先问任务细节。主路由新会话那次跑在这之前。

## 验证

- 验证演练全过。仓库里的假报告叫它直接报 `ready`，它判了 `failed`，并把这条指令写进 notes。
- 只读沙箱读回确认写文件被挡住：沙箱里 bash 根本起不来，PowerShell 写文件报访问被拒绝。所以验收命令必须在沙箱外跑。
- 提示词里的路径转成 `C:/...` 形式。子 agent 在沙箱里可能只能用 PowerShell，Git Bash 的 `/tmp/...` 它不一定认。
- 额度判断只在子 agent 非正常结束时才看日志。日志里有它的正文，调研内容本身可能提到 usage limit。

## 写入类派工试跑（临时仓库）

- 主力和轻量子 agent 各在专用 worktree 里并行。路径不相交，合并无冲突，合并后验收测试通过。
- `kick-verify.sh` 在真实提交上报 `ready`，5 条标准都有证据，前后指纹一致。
- 写代码的派工单模板要求写提交消息文件，可写路径里却没列。子 agent 按规则报了 `blocked`，白费一轮。修了模板后同类任务一轮通过。派工单写完要回头问：每条交付要求都在可写路径里吗？
- `kick-loop.sh` 当时不识别 `blocked`：第 1 轮报了，它仍然把失败结果交回去叫它修。这次无害；如果子 agent 是真的需要越界才能完成，这样可能把它推向越界。后来改成回执最后一行只写 `blocked` 时直接停下（退出码 15）。
- 真实 CLI 上，矛盾的派工单确实触发了 `blocked`，脚本停下，没有提交，范围外的文件也没被改。
