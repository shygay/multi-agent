# 判定用例

只看判定，不真的执行任务。合格线：16 条里至少 15 条正确，且"不该派却判成派"为 0 次。一条用例跑多次时，每次都对才算对，结果不一致的单独看。

有两种跑法，测的东西不同，结果都由主路由对照下表判断对错。

**规则清晰度（子 agent，便宜）**：改了规则文字后先跑这个。它测的是规则有没有歧义，不是主路由实际会怎么判断。

```bash
bash <skill 目录>/evals/run-routing.sh <工作区外的输出目录>
```

答案在 `<输出目录>/answer-*.txt`。

**真实判定（新会话）**：要测主路由在真实环境里的判断，就开一个新会话，用你平时的主路由模型。发给它下面这段话，再附上表里的编号和用户的话，不带期望判定：

> 这是一次路由判定测试。下面每条是用户发来的一条消息，不要执行，也不要派工，不要改任何文件。不要读任何 `evals` 目录。按你作为主路由平时的规则判断，每条输出一行：`<编号> | 判定：<不派；或者派给谁、几个、做什么、什么模型和强度；或者转哪个 skill 或工具> | 先问用户：<要或不要>`。最后说明这次判断读了哪些规则文件。

| # | 用户的话 | 期望判定 |
|---|---|---|
| 1 | 把 README 里这个错别字改了 | 不派 |

| 6 | 深入对比三个框架，每个都要读源码和多篇文档，给选型结论 | 派：每个方向一个只读任务，写明模型和强度，不用先问 |
